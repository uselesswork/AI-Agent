# 第九阶段：资料库与报告历史

核对日期：2026-10-27。

## 目标与实际成果

把原来只在保存投递时写入的简历画像、岗位画像和匹配报告，开放为可独立查看和复用的资料库。网页可保存当前结构化画像、收藏岗位、选择已有简历与岗位重新分析，并查看最近的报告历史。重新分析会调用所选 OpenAI 或 DeepSeek，写入一份新的 `match_reports` 记录；它不会修改旧报告、已保存投递的报告快照或投递状态。

资料库**不保存**上传的 PDF/DOCX/TXT 文件字节，也不向共享的 `resumes.raw_text` 或 `jobs.raw_description` 写原文。需要原文字面证据时，仍按第七阶段的单条投递授权流程处理。

## 页面使用与数据流

1. `/upload` 中完成“生成候选人画像”后，可在页面下方资料库点击“保存当前简历画像”；完成“解析岗位要求”后，可填写可选的岗位链接并点击“保存当前岗位并收藏”。也可以直接使用从以往投递记录关联出来的画像和岗位，不需要再次上传文件。
2. 相同候选人画像按规范化 JSON 的 SHA-256 内容键复用，文件名不参与去重。岗位资料有链接时按规范化链接去重；没有链接时按完整结构化岗位画像精确去重。命中旧投递关联的资料时，会返回已有 ID；这不是语义相似岗位判断。
3. 资料库列出已有简历和岗位。可查看完整结构化 JSON、选择为重新分析输入、切换岗位收藏。只有**未被报告或投递引用**的画像/岗位允许删除；已有报告不会因为删除投递而自动删除，因此删除入口可能返回 409。
4. 选择一份画像和一个岗位，再选择 OpenAI 或 DeepSeek，点击“重新分析并保存报告”。后端读取已保存的两份结构化画像，调用现有匹配分析服务，校验五维报告并插入新记录。此操作可能产生模型费用，网页会在发送前要求确认。
5. “匹配报告历史”显示最近 100 条报告摘要和完整结果查看入口。历史包含先前保存投递时生成的报告和重新分析的新报告；测试数据中的 `manual-test-fixture` 是人工样例，不应误认为大模型结果。

## 接口

| 接口 | 说明 |
| --- | --- |
| `POST/GET /api/library/resumes` | 保存画像（返回 `created` 是否新建）/列出画像。 |
| `GET/DELETE /api/library/resumes/{id}` | 查看/删除画像；仍被引用时删除返回 409。 |
| `POST/GET /api/library/jobs` | 保存岗位（可传 `favorite`）/列出岗位；列表可传 `favorite_only=true`。 |
| `GET/DELETE /api/library/jobs/{id}` | 查看/删除岗位；仍被引用时删除返回 409。 |
| `PATCH /api/library/jobs/{id}/favorite` | 传 `{"favorite": true}` 或 `false` 切换收藏。 |
| `GET /api/library/reports` | 最近 100 条报告；可选 `resume_id`、`job_id` 按组合筛选。 |
| `GET /api/library/reports/{id}` | 完整历史报告。 |
| `POST /api/library/reports/reanalyze` | 传 `resume_id`、`job_id`、可选 `provider`；调用模型并保存新报告。资料缺失返回 404，配置缺失返回 503，模型服务失败返回 502。 |

## 数据库升级

第九阶段只新增 `job_favorites`，字段为 `job_id`（主键、外键指向 `jobs.id`，删除岗位时级联删除收藏）和 `created_at`（UTC 收藏时间）。没有修改 `resumes`、`jobs`、`match_reports`、`applications` 等旧表列。SQLAlchemy 在应用初始化时可创建缺失表；已有 MySQL 库推荐先备份、暂停应用写入，再在 `D:\Agent\job-agent` 显式执行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.upgrade_job_favorites
```

脚本可串行重复执行，不回填收藏、不导入测试数据，也不重跑旧库的画像关联回填。完成后重启后端。MySQL DDL 会隐式提交，不能当作整批事务回滚。

## 验证范围和限制

- 2026-10-27 完整自动化测试 57 项通过，Ruff 和前端 JavaScript 语法检查通过。新增测试使用临时 SQLite、虚构画像和模拟匹配模型，验证精确复用、收藏切换、引用中的删除保护、报告历史和重新分析不改旧投递。
- 真实 MySQL 已用独立脚本增建空的 `job_favorites` 表（0 条）；只读检查确认 `job_id`、`created_at` 和一个外键，简历、岗位、报告列表均能读取。没有在真实 MySQL 写入资料/收藏/报告，没有调用真实 OpenAI/DeepSeek，也没有浏览器端到端测试；上述 SQLite 测试不能替代这些联调。
- 本阶段完成时资料库尚无账号隔离；第十三阶段已加入按账号归属，现有 MySQL 已完成初始账号升级。候选人画像可能含联系方式和经历证据，不能把接口直接暴露公网。
- 去重是规范化链接或结构化内容的精确比较，不做语义相似度、公司同名识别或跨招聘网站的岗位合并。网页保存的岗位如果和旧投递岗位同链接，可复用旧记录；不覆盖其历史画像。当前岗位列表查询和去重会读取全部岗位，海量数据时需要索引及分页优化。
- 重新分析只使用结构化画像，原文不参与新模型调用；模型分数仍需人工核对。新报告不自动变成旧投递的采用报告，也不会重写草稿版本。
- 报告历史列表最多返回最近 100 条，尚无分页、报告对比、独立报告删除和应用内报告切换。资料库只提供保存、查看、收藏和受引用保护的删除，不支持在原记录上直接改写画像。
- 第九阶段交付时，岗位资料仅来自当前用户解析结果与已有记录。第十阶段已增加用户指定 Greenhouse/Lever 公开招聘板后的发现、筛选和来源记录；仍没有全网搜索或任意网页抓取。见[第十阶段说明](第十阶段-公开岗位发现与导入.md)。
