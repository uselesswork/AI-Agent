# 第八阶段：看板搜索与历史回看

核对日期：2026-10-26。

## 目标与成果

在不改变原有七张表、不调用大模型的前提下，改善已保存投递的查找和回看体验：关键词搜索、数据库端排序和分页、完整分析快照回看、状态事件时间线，以及实际投递日期的手动维护。

## 数据流与页面操作

1. 在 `/upload` 的“我的求职看板”输入关键词并点击“搜索”，可查岗位名称、公司、地点或备注；可结合状态筛选和匹配分/更新时间排序。每页最多显示 10 条，按钮翻页。关键词搜索在点击按钮或按 Enter 后生效；清空输入再搜索可恢复全部记录。
2. 前端调用 `GET /api/applications/search`。后端在数据库中完成条件匹配、排序、总数统计及 `LIMIT/OFFSET`，返回本页条目和总数。排序分数优先使用关联报告；旧快照缺少关联时读取快照分数。标题/公司/地点也对缺少关联的旧快照做字段回退。
3. 点击卡片“查看与编辑”，除了原有链接、备注，还能设置或清空实际投递日期。展开时读取已有 `GET /api/applications/{id}` 的完整候选人画像、岗位画像与匹配报告，并以可折叠 JSON 显示；另读取该投递的事件时间线。这里是**已保存快照**，不会重新分析或更新分数。
4. 点击“保存修改”后，日期通过 `PATCH /api/applications/{id}` 写入。手动修改日期会产生 `applied_at_changed` 事件。首次切换至“已投递”且没有手动传日期时，仍沿用旧逻辑自动记录当前 UTC 日期；显式清空日期后，仅修改备注等字段不会重新补回日期。历史无法确认的旧记录继续为 `null`，不根据当前状态推断日期。

## 接口约定

| 接口 | 用途与主要参数 |
| --- | --- |
| `GET /api/applications/search` | `q` 最长 100 字符；`status` 为六种状态之一；`sort` 为 `updated_desc`、`score_desc`、`score_asc`；`page` 从 1 开始；`page_size` 为 1～100，默认 10。返回 `items`、`total`、`page`、`page_size`。 |
| `GET /api/applications/{id}/events` | 返回所属投递事件，按时间及 ID 倒序；投递不存在时 404。 |
| `PATCH /api/applications/{id}` | 新增可选 `applied_at`，格式为 `YYYY-MM-DD` 或 `null`；省略表示不修改。 |
| `GET /api/applications` | 原有数组返回保持不变，供旧调用方继续使用；新的前端看板改用 `/search`。 |
| `GET /api/applications/{id}` | 原有完整详情继续使用；响应现在包含可空的 `applied_at`。 |

## 验证范围

2026-10-26 完整自动化测试 53 项通过，Ruff、前端 JavaScript 语法和差异空白检查通过。新增测试使用临时 SQLite 数据库和人工夹具，覆盖组合筛选、按分数翻页、旧快照字段回退、空搜索结果、分页参数 422、事件列表、日期设置/清空、旧列表兼容。真实 MySQL 只读验证了默认分页、关键词匹配、分数排序和事件读取；没有修改真实库数据。前端测试只验证页面和脚本入口，脚本语法检查只验证语法；没有执行浏览器端到端操作、真实 MySQL 日期写入或大模型联调。

## 限制与后续维护

- 看板仍是无登录的本地单用户页面；完整快照可能含个人信息，不应直接暴露公网。
- 搜索是数据库 `LIKE` 包含匹配，不是全文索引；大量记录时可能需要专用索引或搜索服务。分页使用偏移量，频繁同时增删记录时跨页结果可能变化。
- 历史报告按完整 JSON 展示，尚未做独立的可视化历史报告页、报告差异或重新分析工作流；这属于第九阶段规划。
- 时间线只记录已有的创建/状态变更/迁移快照，以及本阶段起的手动投递日期修改。以前仅修改备注和链接的操作没有历史事件，不可追溯。
- 没有新增面试日期、截止日期或提醒功能；这仍属后续规划。
- 更改搜索字段、分页或日期语义时，同步更新根目录 README、网页端指南、数据库字段说明、接口测试和本文件。文档中的验证结果必须注明使用临时 SQLite 还是真实 MySQL。
