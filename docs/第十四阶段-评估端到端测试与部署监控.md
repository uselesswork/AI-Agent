# 第十四阶段：模型评估、浏览器端到端测试与本地部署监控

## 一眼看懂本阶段

本阶段补上三条工程化路径：用虚构案例离线检查模型输出的结构、字面证据和评分一致性；用真正的浏览器走登录、简历解析、看板隔离和退出；为本地运行增加数据库就绪检查、最小化访问日志和可选 Docker Compose 配置。它们帮助发现回归问题，但不会自动证明模型判断正确，也不表示已经完成公网生产部署。

评估默认不调用模型、不读真实简历、不产生 API 费用。只有显式添加 `--live --provider openai|deepseek` 才会调用对应服务商。OpenAI 官方文档建议为应用建立明确目标、数据集和评价指标；旧 Evals 平台正在弃用，因此这里使用项目内可重复运行的轻量评估器，不依赖其平台接口。参考：[OpenAI 官方评估实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。

## 文件与职责

| 文件 | 作用 |
| --- | --- |
| `job-agent/app/services/evaluation.py` | 校验画像、岗位和匹配报告结构；检查证据是否为原文片段、预期技能/要求、最低证据数量及评分加权近似 |
| `job-agent/evals/cases.json` | 三个完全虚构的简历、岗位和匹配评估案例，包含输入、参考期望和离线输出 |
| `job-agent/scripts/evaluate_outputs.py` | 命令行离线评估；显式 `--live` 时调用选定的 OpenAI 或 DeepSeek，终端只显示检查结果，不保存原始模型输出 |
| `job-agent/tests/test_evaluation.py` | 离线正例、伪造证据、证据缺失、结构错误、评分不一致和默认不调用模型的回归测试 |
| `job-agent/tests/test_browser_e2e.py` | 独立 SQLite + 临时 HTTP 服务 + Playwright 真实浏览器，验证登录、看板、TXT 解析、跨账号隔离与退出 |
| `job-agent/tests/conftest.py`、`pyproject.toml` | 浏览器测试显式开关和可选 Playwright 依赖，普通单元测试不自动启动浏览器；修正开发依赖中 HTTPX 的包名和版本范围 |
| `job-agent/app/core/observability.py`、`app/main.py` | 给响应添加请求 ID，记录不含个人内容的访问日志；增加只读 `/ready` 就绪接口 |
| `job-agent/tests/test_operational.py` | 就绪接口和访问日志不记录查询参数/Cookie 的测试 |
| `job-agent/Dockerfile`、`compose.yaml`、`.dockerignore`、`.env.docker.example` | 可选本地容器配置：非 root 用户、只读文件系统、本机端口、就绪探针和独立环境示例 |
| `job-agent/tests/test_deployment_config.py` | 静态检查容器配置，不替代实际镜像构建与运行 |

## 数据流与接口边界

离线评估读取 `evals/cases.json` 中的虚构输入与预置输出，经现有 Pydantic 数据模型和独立规则评估器处理，只在终端显示用例 ID、通过状态与失败检查项；不写数据库或发送网络请求。显式真实评估则把虚构输入交给现有简历、岗位和匹配分析服务，再用同一套规则检查返回结果，但仍不保存报告。

浏览器用例先创建独立的临时 SQLite 和虚构账号、投递，再在本机随机端口启动当前 FastAPI 应用；Edge 通过实际 `/upload` 页面执行登录、解析、看板读取和退出。临时数据随测试结束清理。运行监控的数据流是请求进入中间件后生成请求 ID，响应携带 `X-Request-ID`，服务端只记录脱敏访问摘要。新增公开只读接口 `GET /ready`：数据库、账号和第十三阶段来源表结构满足条件时返回 200，否则返回 503；它不检查模型服务可用性。现有 `GET /health` 仍只返回进程健康状态。

## 一、运行模型输出评估

在 `D:\Agent\job-agent` 运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.evaluate_outputs
```

默认读取 `evals/cases.json` 的虚构数据，终端显示每个案例及通过的总数。失败时返回非零退出码，可用于本地回归或持续集成。规则主要检查：Pydantic 严格结构、引用片段在简历或岗位文本中的字面存在、测试案例标注的技能/要求、至少应有的证据条数、匹配维度加权分与总分的差距。字面命中**不能**证明经历真实、语义正确或评分公平；开放式摘要、建议和隐含事实仍需人工审核。案例可继续增加，避免只针对一个示例优化。

只有主动愿意调用真实模型、接受网络请求与费用时，才运行下面的可选命令之一：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.evaluate_outputs --live --provider openai
.\.venv\Scripts\python.exe -X utf8 -m scripts.evaluate_outputs --live --provider deepseek
```

真实评估仍使用相同虚构案例，分别经过现有模型分析服务；需在本机配置对应 API Key。脚本不打印简历正文或模型原始输出，但服务商会接收案例输入。不要将真实个人资料直接放入可提交的案例文件；若以后用于个人数据，先征得同意、去标识化并控制报告保存位置。本次**没有执行真实模型评估**。

## 二、运行真实浏览器测试

可选依赖安装和执行命令：

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[dev,e2e]"
.\.venv\Scripts\python.exe -m pytest tests/test_browser_e2e.py --run-browser-e2e -q
```

Windows 本机若安装 Microsoft Edge，测试会优先用 Edge；其他环境可先运行 `.\.venv\Scripts\python.exe -m playwright install chromium`。浏览器测试使用随机本机端口、临时 SQLite 和虚构账号，**不会连接现有 MySQL，也不会调用 OpenAI/DeepSeek**。普通 `pytest` 默认跳过这个浏览器用例，只有 `--run-browser-e2e` 才真正启动浏览器。参考：[Playwright Python 官方文档](https://playwright.dev/python/docs/library)。

当前浏览器用例覆盖登录遮罩、登录后原有看板记录、TXT 简历上传解析、第二账号看不到第一账号投递，以及退出后重新出现登录遮罩。尚未覆盖全部 PDF/DOCX、模型页面结果、定制材料下载和不同浏览器内核；后续应逐步扩充。测试不使用真实账号密码。

## 三、本地运行、部署和监控

不使用容器时，在项目目录运行：

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

`GET /health` 只说明进程在响应；新增 `GET /ready` 会只读检查数据库连接、至少一个账号和 `job_imports.user_id` 字段。成功时返回 200 `{"status":"ready"}`，失败时返回 503 `{"status":"unavailable"}`，不回传连接地址或密码。它不是模型网络、浏览器或全部业务接口的端到端检查。访问日志只记录服务端生成的请求 ID、方法、路由模板、状态码和耗时，不记录请求体、查询参数、Cookie 或用户名；响应含 `X-Request-ID` 便于定位问题。建议使用 `--no-access-log` 禁用 Uvicorn 自带的原始 URL 日志。

可选 Docker Compose 文件只绑定 `127.0.0.1:8000`，不自动创建或迁移数据库，也不内置任何密码。若已有独立、可从容器访问的 MySQL 账号，在确认备份与访问权限后复制 `.env.docker.example` 为被 Git 忽略的 `.env.docker`，填写**容器视角**的数据库地址和所需模型 Key；Windows Docker 容器访问宿主机通常用 `host.docker.internal`，不能直接使用原 `.env` 中的 `127.0.0.1`。避免使用数据库 `root` 账号。然后可运行：

```powershell
docker compose up --build -d
docker compose ps
docker compose logs -f app
docker compose down
```

容器以非 root 用户运行、根文件系统只读，并用 `/ready` 做健康探针。`.env.docker` 仍是本机明文配置，应控制权限，不能提交 Git，更不能写入网页登录密码。当前环境的 Docker 引擎未启动，因此**没有实际构建或运行容器**；静态配置测试通过不等于容器部署成功。公网服务还需要 HTTPS、反向代理可信来源、登录限流、备份恢复演练、密钥管理和安全审查；本阶段只提供可信本机部署基础。

## 实际验证和限制

- 离线评估的三个虚构案例运行通过；规则反例由临时测试验证。该结果只说明评估器和夹具自身可运行，不代表 OpenAI/DeepSeek 的真实输出质量。
- 真实浏览器端到端测试已在本机 Edge 运行，使用临时 SQLite 和虚构数据；不代表现有 MySQL 的网页登录联调或实际模型测试。
- 普通自动化测试 88 项通过、1 项浏览器用例按设计跳过；另行显式运行的本机 Edge 浏览器用例 1 项通过。Ruff、前端脚本语法、依赖一致性、差异空白和本地 Markdown 链接检查通过。
- `/ready`、最小化日志与部署文件有自动化/静态测试；现有真实 MySQL 的 `GET /ready` 只读检查返回 200 `{"status":"ready"}`，并未使用真实账号登录或修改数据。Docker 引擎未运行，不能宣称容器上线。
- 没有加入外部监控平台、告警、分布式追踪、定时自动评估或公网部署。日志不会包含业务数据，但仍应限制日志文件访问；不要把错误堆栈和 `.env` 上传到公开平台。
