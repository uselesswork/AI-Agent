## 目标与现状

让数据库相关行为在隔离的 MySQL 测试库中可重复验证，并在提交代码时自动运行检查。现有 `tests` 已覆盖大量接口与账号隔离，但主要使用临时 SQLite；`tests/test_browser_e2e.py` 也使用临时 SQLite。第十四阶段记录的真实 MySQL 检查仅限 `/ready` 等只读请求，不能证明登录后读写、事务和删除行为。当前仓库尚无 CI 工作流。

## 数据流与实施步骤

1. 为测试创建**独立**的 MySQL 库和受限账号；测试启动时核对库名或专用标记，拒绝连接当前日常数据库。只使用虚构简历、岗位和账号。
2. 从当前表声明建立测试库结构，再走真实 HTTP 登录、Cookie/CSRF、资料保存、投递状态变更、跨账号读取拒绝、删除级联及事务失败回滚。对关键结果从数据库回读，不只检查响应码。
3. 同一用例分别在临时 SQLite 与 MySQL 下运行适用部分，明确记录数据库方言差异。不得把 SQLite 通过写成 MySQL 通过。
4. CI 使用临时 MySQL 服务，不读取本地 `.env`，不配置真实模型 API Key；运行 `ruff check`、普通 `pytest` 和单独标记的 MySQL 测试。浏览器及真实模型用例继续作为显式步骤。

## 完成标准与验证范围

- 本地隔离 MySQL 测试库和 CI 均能从空环境重复通过；失败退出码会使 CI 失败。
- 至少覆盖登录/退出、CSRF、两账号隔离、投递新增与状态事件、删除级联、失败回滚和 `/ready`。
- 输出记录测试库类型、用例数和 CI 结果；不输出密码、会话令牌、简历正文或 `.env` 内容。
- CI 通过只证明虚构数据与测试库上的回归，不证明真实模型质量或用户日常库的数据正确性。

## 限制与依赖

需先设计安全的测试库隔离和清理机制。当前日常 MySQL 库中的真实账号不作为自动化测试凭据；若要验证该账号，仍需用户在网页上自行登录。参考：[GitHub Actions 的 Python 构建与测试说明](https://docs.github.com/en/actions/tutorials/build-and-test-code/python)。
