## 一眼看懂

保存投递记录时，用户可以明确勾选“留存简历解析正文和岗位描述”。只有勾选并同时提供两份原文，后端才将它们保存到该投递专属的 `application_sources` 表；默认不留存。已保存草稿版本可逐行做保守的字面片段检查，显示来自简历、来自岗位或未命中，并附原文片段。还可比较两个版本的简历与求职信文本差异。用户可以单独删除留存原文，不影响投递记录和草稿版本。

这不是自动事实核验。字面命中只能说明某段文字出现在原文中；岗位原文命中绝不能作为候选人经历的证明。未命中也不能断定内容虚构，改写后的真实经历可能无法字面匹配。系统不会根据报告自动批准或拒绝投递。

## 数据流与隐私边界

1. 用户上传简历，可先用“开始解析”得到正文，再完成候选人画像、岗位解析和匹配。第七阶段不会改变原有解析或模型调用行为。
2. 保存到看板时，默认不勾选原文留存，每次成功保存后也会清除勾选；未勾选时请求只保存原有结构化快照。勾选时，前端提交简历解析正文与岗位描述，后端要求两者均非空。简历正文最多 1000000 字符，岗位描述最多 30000 字符；原上传文件本身仍不保存。
3. 原文写入 `application_sources`，以 `application_id` 为主键。候选人画像可能在多个投递间复用，所以不把本次原文写进共享的 `resumes.raw_text` 或 `jobs.raw_description`，防止跨投递混用。
4. 看板读取留存状态；对某个已保存草稿版本请求证据报告。后端逐行查找去除空白、忽略英文大小写后的完整行。长度不足 8 个规范化字符不算证据；先查简历原文，再查岗位原文。结果附一小段原文上下文和起始字符位置，不返回整份原文。
5. 用户可点“删除留存原文”撤回留存；表行被删除，第十一阶段可能附加的人工标注也会删除，历史草稿和投递仍保留，之后证据接口返回 409。删除整条投递时原文随外键级联删除。
6. 两个历史版本的比较只读取已保存的草稿 JSON，展示增删行，不需要留存原文，也不调用大模型。

旧投递记录没有原文，不能根据结构化画像“补造”原始文本。留存状态和证据接口不会向旧记录推断来源。系统是无登录的单用户本地项目，不应将含个人信息的接口直接暴露公网；重要数据应自行备份并控制本机访问权限。

## 新接口

| 方法与路径 | 作用 |
| --- | --- |
| `POST /api/applications` | 沿用原接口；可选提交 `retain_source_text: true`、`resume_text`、`job_description`。无显式同意时拒绝原文字段。 |
| `GET /api/applications/{id}/sources/status` | 仅返回 `retained` 布尔值，不返回原文。 |
| `DELETE /api/applications/{id}/sources` | 删除该投递留存原文；重复执行仍返回 204。 |
| `GET /api/applications/{id}/draft-versions/{version}/evidence` | 对已保存版本逐行返回字面查找结果；无留存原文返回 409。 |
| `GET /api/applications/{id}/draft-versions/compare?from_version=1&to_version=2` | 返回简历和求职信的文本差异；版本不存在返回 404。 |

接口严格区分“简历原文命中”“岗位原文命中”“未命中”。命中不等于语义证据或真实经历核验；证据片段仍可能含个人信息，只在本地受控环境查看。

## MySQL 升级与验证

已有库先备份，暂停应用写入，再在 `D:\Agent\job-agent` 执行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m scripts.upgrade_application_sources
```

脚本只增建缺失的 `application_sources`，可串行重复执行；不回填旧记录、不导入测试数据。应用仓储首次初始化也会创建缺失表，但显式升级便于检查。完成后重启后端。完整初始化脚本 `scripts.init_database` 仍有旧数据关联回填及六条虚构记录导入步骤，作用范围不同。

2026-10-26：自动化测试 50 项通过，Ruff、前端 JavaScript 语法及差异空白检查通过。新增测试使用临时 SQLite 和人工文本，覆盖默认不留存、缺少同意时拒绝原文、同画像投递隔离、字面命中与未命中、版本差异、单独删除原文和删除投递时级联；不能等同于真实模型/MySQL 写入联调。

真实 MySQL 已增建空表，原六表计数仍为 `1/6/6/6/6/0`，新表 0 条。只读结构检查确认 `application_id` 主键、两列 `LONGTEXT`、`stored_at`，以及指向 `applications` 的 `CASCADE` 外键。FastAPI TestClient 连接真实库读取六条投递返回 200，旧记录原文状态返回 200 且 `retained=false`。未向真实 MySQL 写入简历/JD 原文或测试证据，未执行浏览器端到端操作，也未调用大模型。

## 尚未实现

- 第十一阶段已有版本单行人工来源关联表，但仍没有语义蕴含判定或事实真实性审查；字面命中和人工关联均不能自动决定是否可以投递。
- 不把原文中的每个事实自动映射到候选人画像字段；只针对草稿版本逐行做字面检查。
- 没有全文搜索、来源文件字节留存、版本差异的图形化行内高亮或浏览器端到端自动化测试。
- 旧记录若需证据检查，需要用户重新上传/解析并创建经明确同意留存原文的新投递；不会静默回填旧记录。
