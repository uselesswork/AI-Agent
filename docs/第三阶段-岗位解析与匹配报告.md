## 2. 具体完成的工作

### 2.1 结构化岗位描述

用户粘贴 JD（岗位描述），前端显示字符数并提交。后端要求 `description` 为 20～30000 字符，通过模型提取 `JobProfile`：

| 字段 | 含义 |
| --- | --- |
| `title`、`company`、`location` | 岗位名称、公司、地点 |
| `responsibilities` | 职责 |
| `required_skills`、`preferred_skills` | 必备技能、加分技能 |
| `education`、`experience` | 学历、经验要求 |
| `internship_duration` | 实习周期等时间要求 |
| `requirements` | 逐项结构化要求 |
| `warnings` | 不确定或需确认的信息 |

每个 `JobRequirement` 包含名称、类别、重要性、原文证据。类别为技能、学历、经验、时间、地点、其他；重要性为必须、加分。

### 2.2 生成匹配报告

匹配接口直接接收候选人画像和岗位画像，不重新上传简历。`MatchResult` 包含：

- `overall_score`：0～100 总分。
- `recommendation`：建议投递、谨慎投递、暂不建议投递。
- `summary`：总体分析。
- `dimensions`：维度名称、分数、权重、理由。
- `assessments`：每条要求的判断、理由、简历证据、岗位证据。
- `strengths`、`gaps`：优势、差距。
- `resume_suggestions`：针对岗位的简历改进建议。
- `warnings`：不确定信息。

逐项判断限定为满足、部分满足、不满足、无法确认。

### 2.3 评分维度与约束

| 维度 | 提示词指定权重 | 分析方向 |
| --- | --- | --- |
| 技能匹配 | 35% | 技术栈与要求是否对应 |
| 项目经验 | 25% | 项目内容与职责的关联 |
| 教育背景 | 15% | 学历、专业等 |
| 实习经历 | 15% | 实践经历的相关性 |
| 基本条件 | 10% | 地点、时间等条件 |

提示词要求总分是维度加权结果，四舍五入为整数，并要求不虚构经历。

后端实际强制检查：

1. 分数、权重为 0～100 范围内的整数。
2. 五个维度齐全、不重复。
3. 权重之和为 100。
4. 字段类型及枚举符合模型。

目前后端没有强制每项权重等于上表，也没有重新计算或核对总分。这是模型辅助评分，不是独立的确定性规则评分引擎。

### 2.4 前端报告与模型选择

- 完成候选人画像后显示岗位输入区。
- 提供字符统计和“解析岗位要求”按钮。
- 岗位预览展示名称、公司、地点、学历、技能和职责。
- 增加匹配报告独立模型选择器。
- 展示总分、投递建议、概述、五维评分卡片、优势、差距和简历建议。
- 逐项要求显示判断和解释，简历证据可展开。
- 保留 `currentJobProfile`、`currentMatchData`，供第四阶段保存。

## 4. 数据流

```text
岗位文本 + provider → /api/jobs/parse
→ JobAnalyzer → 提示词 + Schema → 统一客户端
→ JobProfile 校验 → 页面岗位预览

CandidateProfile + JobProfile + provider → /api/matches/analyze
→ MatchAnalyzer → 提示词 + Schema → 统一客户端
→ MatchResult 校验 → 页面报告
```

两个接口分别构建分析器，服务商可以不同；匹配接口也不要求两个输入画像来自同一家服务商。

## 5. 接口契约

### 5.1 岗位解析

`POST /api/jobs/parse`，JSON 请求示例：

```json
{
  "description": "招聘 Python 后端开发实习生，熟悉 FastAPI 和 SQL，每周到岗四天。",
  "provider": "deepseek"
}
```

响应包含 `provider`、`model`、`profile`，其中 `profile` 是 `JobProfile`。

### 5.2 匹配分析

`POST /api/matches/analyze`，JSON 字段如下：

| 字段 | 必填 | 来源 |
| --- | --- | --- |
| `candidate_profile` | 是 | 简历分析响应的 `profile` |
| `job_profile` | 是 | 岗位解析响应的 `profile` |
| `provider` | 否 | 本次匹配选择的服务商 |

响应包含 `provider`、`model`、`result`，`result` 为完整匹配报告。

两接口均可返回：请求校验错误 `422`、配置错误 `503`、模型服务或输出结构错误 `502`。

## 6. 模型选择行为

| 操作 | 使用选择器 | 代码 |
| --- | --- | --- |
| 候选人画像 | 第二阶段选择器 | `selectedProvider()` |
| 岗位解析 | 第二阶段选择器 | `selectedProvider()` |
| 匹配报告 | 岗位预览下方独立选择器 | `selectedMatchProvider()` |

独立选择器创建时默认跟随前面的选择，随后可以单独修改。重新解析岗位会重建该选择器。接口省略服务商时，后端才使用 `LLM_PROVIDER`。

## 8. 当前边界

- 不自动抓取招聘网站，用户手动粘贴 JD。
- 岗位预览尚未完整展示 `requirements`、`experience`、`internship_duration`、`warnings` 等全部字段。
- `job_evidence` 和匹配 `warnings` 已在模型中定义，页面尚未专门展示。
- 原文引用真实性、全部要求是否逐项覆盖，目前没有程序化核验。
- 匹配依赖画像，抽取时遗漏的原始信息可能影响评分。
- 前端旧结果失效、并发请求和结果绑定仍可加强；更换输入后应重新分析再保存。
- 没有批量岗位分析、自动投递或统一的跨岗位校准机制。

## 9. 后续维护

修改维度需同步模型、提示词、前端和测试；改变模型选择行为需更新本文件与根目录 README；增加报告字段还需检查第四阶段保存结构。
