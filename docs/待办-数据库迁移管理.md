# 待办：数据库迁移管理

> 状态：待实现。本文不包含可直接执行的迁移命令；现有数据库尚无 Alembic 版本记录。
> [返回项目说明](../README.md) · [数据库设计与字段说明](数据库设计与字段说明.md)

## 目标与现状

为后续表结构变更建立可审查、可重复的版本链。当前十四张表由 `app/core/database_schema.py` 声明；历史升级依赖 `scripts/init_database.py` 和多个 `scripts/upgrade_*.py`。这些脚本按阶段解决过具体升级，但没有统一的迁移版本表，无法仅凭数据库状态判断下一次该执行哪一版。

## 计划涉及的文件与职责

| 文件或目录 | 计划职责 |
| --- | --- |
| `job-agent/app/core/database_schema.py` | 保持当前结构声明，供迁移工具比较目标元数据 |
| 待新增 `job-agent/alembic/`、`alembic.ini` | 保存迁移环境、基线版本及后续逐版脚本 |
| `job-agent/scripts/upgrade_*.py` | 保留为历史升级说明；明确哪些旧库需要先执行旧脚本，避免与新迁移重复 |
| `job-agent/tests/` | 验证空库升级、现有结构纳入版本管理及一次前向结构变更 |

## 迁移路径

1. 先盘点空库、完整十四表库和各历史阶段库的结构差异，确定支持哪些起点。不要直接给未知结构的库标记最新版本。
2. 为**已核对与当前元数据一致**的十四表库建立基线；为全新空库提供从零升级到最新版本的路径。旧阶段库须先走经过验证的过渡步骤。
3. 后续每次字段、索引或约束变更单独提交迁移文件，与应用代码和字段文档同次更新。自动生成结果须人工检查，尤其是 MySQL 类型、约束名和数据回填。
4. 在隔离 MySQL 库演练升级；对有数据的库先备份、停写、核对升级前后行数和关键关系，再记录版本号。MySQL DDL 会隐式提交，不能把整次结构升级视作一个可回滚事务。

## 完成标准与验证范围

- 空 MySQL 库能按版本链建立完整十四表结构；已有完整库通过结构检查后纳入版本记录，业务数据不被重建。
- 至少用一项真实的示例结构变更验证升级步骤、重复执行处理和失败恢复文档；记录不支持自动回退的操作。
- 自动化测试使用独立测试库，不在日常数据库演练破坏性迁移。
- 文档明确旧阶段脚本与新迁移命令的适用范围，防止重复建表或导入测试数据。

## 限制与依赖

现有脚本含历史数据认领和样例导入逻辑，不能简单改名为迁移版本。需要先完成真实 MySQL 结构核对，再确定基线。参考：[Alembic 官方迁移教程](https://alembic.sqlalchemy.org/en/latest/tutorial.html)及[自动生成迁移的限制](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)。
