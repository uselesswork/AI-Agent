验证另一台开发机能依据文档启动项目，并明确容器、MySQL 和环境配置之间的依赖。编写计划时 `Dockerfile`、`compose.yaml`、`.env.docker.example` 仅提供本机容器配置，`tests/test_deployment_config.py` 只做静态检查。第十四阶段记录的 Docker 引擎未运行；第十八阶段已在本机完成实际演练，但尚未在第二台机器复跑。

## 演练步骤

1. 使用独立测试 MySQL 库和受限连接账号；准备已初始化的结构与虚构登录账号，不连接日常业务库。确认容器视角的数据库主机地址，不能把宿主机 `127.0.0.1` 直接当作容器内数据库地址。
2. 在本机实际执行镜像构建和 Compose 启动，检查容器状态、`/health`、`/ready`、`/upload` 与静态资源。服务启动成功但 `/ready` 失败时，分别排查账号、结构和数据库连接。
3. 用虚构账号人工完成登录、保存一条测试投递和重新读取；重启容器后再次读取，确认数据由 MySQL 持久化。记录构建时间、镜像大小和关键失败原因。
4. 检查访问日志不输出 Cookie、密码、查询参数或简历正文。演练停止、重新启动和恢复流程；将实际命令与结果写回 README 和第十四阶段文档。

## 完成标准与验证范围

- 一台干净开发机可按文档构建、启动、访问并停止；健康探针显示正常。
- 容器重启后虚构测试投递仍存在；登录与业务读写在隔离 MySQL 库中通过。
- 文档记录操作系统、Docker/Compose 版本、测试范围和问题；不记录真实密钥、数据库密码或 `.env.docker` 内容。
- 该演练只证明本机容器运行，不等于公网生产部署。公网开放仍需 HTTPS、登录限流、备份恢复和安全检查。

## 限制与依赖

先完成独立测试库和初始账号准备；如果要验证真实模型，还需另行显式配置服务商凭据并标记费用与数据发送范围。容器编排不负责自动创建或迁移数据库。
