> 核对日期：2026-11-18。本机隔离 MySQL 的建表、旧库接入与增量升级已验证；日常 `job_agent` 库只做只读结构检查，尚未标记迁移版本。

## 一眼看懂本阶段

项目新增 Alembic 迁移链。`0001_current_schema` 冻结原十四张表；`0002_user_assets_owner_index` 为 `user_assets(user_id, entity_type, entity_id)` 增加复合索引，服务于按账号和资料类型查找归属 ID。全新空库可按迁移链建表；旧十四表库须先通过结构核对，再登记基线并执行索引升级。旧阶段的 `upgrade_*.py` 保留供更早版本库参考，不与新迁移脚本混用。

## 文件与职责

| 文件 | 职责 |
| --- | --- |
| `job-agent/alembic.ini`、`alembic/env.py`、`alembic/script.py.mako` | Alembic 配置、项目环境变量连接、版本脚本模板；配置文件不保存数据库密码 |

| `.github/workflows/python-ci.yml` | 在临时 MySQL 服务上运行迁移测试和原有真实会话集成测试 |

## 迁移路径与数据流

先在 `D:\Agent\job-agent` 安装依赖，并通过 `.env` 的 `DATABASE_URL` 指向**要检查的 MySQL 库**。下列 `status` 只读，适合先确认状态：

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -X utf8 -m scripts.manage_migrations status
```

| 库状态 | 命令 | 行为 |
| --- | --- | --- |
| 完全空库 | `python -m scripts.manage_migrations initialize` | 顺序执行 `0001`、`0002`，建十四张业务表和 `alembic_version`，不创建登录账号或测试记录 |
| 无版本记录且结构符合旧十四表基线 | `python -m scripts.manage_migrations adopt` | 检查表集合、主键、唯一约束及 Alembic 元数据差异；登记 `0001`，执行 `0002`，前后核对业务行数 |
| 已有迁移版本 | `python -m scripts.manage_migrations upgrade` | 从已登记版本升级到当前经审查的最新版本；重复执行最新版本不会重复建索引 |
| 结构不符或更早阶段库 | 暂不执行上述写命令 | 按原阶段文档核对并完成旧升级，再重新运行 `status` |

**`adopt` 或 `upgrade` 前应备份并停止应用写入。** MySQL DDL 隐式提交，命令失败不能视为整体回滚。若登记 `0001` 后索引升级失败，应先运行 `status` 并检查 `alembic_version` 与索引；只有确认索引尚未创建且库处于完整基线时才重跑 `upgrade`。若索引已存在、版本仍停在 `0001`，需人工核对并从备份或经审查的修复步骤恢复，不能盲目重复运行。`initialize` 仅接受没有任何表的数据库，不会覆盖旧数据；若在建表中途失败，需核对并清理该新库的残留结构后再初始化。

## 接口与兼容边界

本阶段没有新增 HTTP 接口或前端按钮。`user_assets` 新索引只影响查询路径，不改变业务字段或数据。`scripts/init_database.py` 含历史回填及样例数据逻辑，不作为新迁移入口；账号已启用后它仍拒绝写入。`scripts/upgrade_user_access.py` 仍用于尚未完成第十三阶段的旧库，不能把未核对的旧结构直接标记为 `0001`。未来新增迁移时，须同时更新当前 SQLAlchemy 声明、迁移文件、`manage_migrations.py` 的已审查版本与基线差异说明、README 和对应阶段文档；自动生成的候选迁移需人工检查。

## 实际验证和限制

- 本机随机独立 MySQL 测试库：空库升级到 `0002` 后共 14 张业务表、1 张版本表，结构与当前声明无差异；初始化后可创建虚构账号，重复 `upgrade` 不重复更改。
- 另一个随机独立 MySQL 库先创建旧十四表和虚构账号，`adopt` 后账号行数保持 1，版本到 `0002`；模拟删列后接入被拒绝，且未创建版本表。
- 原有真实会话与投递测试及新增迁移测试共 6 项在隔离 MySQL 通过，覆盖已登记 `0001` 的正常升级与漂移拒绝。普通套件 88 项通过、7 项按设计跳过（浏览器与 MySQL），Ruff 检查通过。真实模型、浏览器与生产迁移不在该结果范围内。
- 当前日常 MySQL 库的 `status` **只读**通过：未登记版本，结构符合 `0001`；没有在该库执行 `adopt`、建索引或改动业务行。将其纳入迁移管理仍需备份、停写并由管理员执行。
- 第十六阶段修改尚未触发远端 GitHub Actions；本阶段 CI 结果以本机隔离 MySQL 为准。随机测试库在运行后只读确认剩余 0 个。
- `0001` 的降级操作被禁用，防止误删十四张业务表；`0002` 仅支持移除新增索引。当前没有自动备份、跨 SQLite/MySQL 数据迁移或对任意历史阶段库的一键升级。
